📊 Vulnerable vs Secure — Code Comparison
🔴 Vulnerable (string concatenation)
// ⚠️ VULNERABILITY: raw user input embedded in SQL string const sql = `SELECT * FROM sqli_demo_users` + " WHERE username = '${username}'" + " AND password = '${password}'"; // If username = ' OR '1'='1' -- then sql becomes: // WHERE username = '' OR '1'='1' --' AND password = '...' // ↑ always TRUE ↑ rest commented out
🟢 Secure (parameterised query)
// ✅ FIX: ? placeholders — user input bound separately const user = db.prepare(` SELECT * FROM sqli_demo_users WHERE username = ? AND password = ? `).get(username, password); // Payload ' OR '1'='1' -- is treated as a LITERAL string. // No row matches username = "' OR '1'='1' --" → login fails.
📖 How SQL Injection Works — Theory

🔴 The Attack

A SQL Injection attack occurs when user-supplied input is embedded directly into an SQL query string without sanitisation. The attacker ends the intended string literal with a single quote ' and appends arbitrary SQL clauses.

Payload: ' OR '1'='1' --

Original intent:
WHERE username = 'alice' AND password = 'secret'

What actually executes:
WHERE username = '' OR '1'='1' --' AND password = 'x'

The -- comments out the password check. '1'='1' is always TRUE, so every row is returned — authentication bypassed.

🟢 The Fix

Parameterised queries (also called prepared statements) separate SQL code from data. The ? placeholder is a typed value slot — the database driver ensures user input is never parsed as SQL syntax, regardless of what characters it contains.

Even with the attack payload:
username = "' OR '1'='1' --"

The database searches for a row where the username column literally equals the string ' OR '1'='1' --. No such account exists → authentication fails → no bypass.
Additional defences:
  • Hash passwords with bcrypt (never compare plaintext)
  • Validate and whitelist user inputs
  • Use an ORM (Object-Relational Mapper)
  • Apply least-privilege database accounts
  • Enable a Web Application Firewall (WAF)
🎓 Viva / Demonstration Guide
  1. Open this page and ensure the server is running on localhost:3000.
  2. Select 🔴 Vulnerable Mode using the toggle at the top.
  3. Click the payload chip ' OR '1'='1' -- to auto-fill the username field. Leave any value in the password field.
  4. Click Attempt Login and observe:
    • The Live SQL Query panel shows the full injected string.
    • The Result panel shows Authentication Bypassed ⚠️.
    • A user account is returned even though no valid credentials were supplied.
  5. Switch to 🟢 Secure Mode.
  6. Use the same payload — click ' OR '1'='1' -- again.
  7. Click Attempt Login and observe:
    • The SQL panel shows the ? template — user input is NOT in the SQL string.
    • The Result panel shows Attack Blocked 🛡️.
    • Explain that the payload was treated as a literal value, not SQL code.
  8. Use a legitimate credential chip (e.g. demouser / demopass) in Secure Mode to show that normal login still works.
  9. Scroll to the Vulnerable vs Secure — Code Comparison card and walk through the annotated code.
  10. Point to the How SQL Injection Works section to explain the theory.
